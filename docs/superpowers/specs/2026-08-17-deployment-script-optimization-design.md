# StarPay 部署脚本交互化与安全增强设计

## 背景

当前 `scripts/deploy.sh` 提供可靠的 `install` 和 `update` 非交互命令，具备生产配置生成、配置校验、并发锁、PostgreSQL 备份和 HTTP 健康检查。它适合自动化和熟悉项目的运维人员，但首次使用缺少引导，更新失败后也不会恢复上一版本。

本次参考 `james-6-23/codex2api` 的交互式部署体验，只吸收部署状态识别、分步向导、复用现有配置、部署摘要和结果提示等设计。不会引入远程脚本执行、自动克隆、`git reset --hard`、明文展示密钥或默认公网监听。

## 目标

1. 无参数运行 `scripts/deploy.sh` 时提供中文交互向导。
2. 保持现有 `install`、`update` 命令和参数向后兼容。
3. 支持拉取预构建镜像和从当前源码本地构建两种发布来源。
4. 更新前创建并校验 PostgreSQL 备份，自动保留最近若干份。
5. 部署失败时自动恢复部署前的 API 镜像。
6. 记录不含密钥的部署元数据，便于排障和审计。
7. 对新增行为提供无需真实修改生产服务的自动化测试。

## 非目标

- 不实现远程 `curl | bash` 自举安装。
- 不自动修改、拉取或重置 Git 仓库。
- 不在本次增加 GHCR 镜像发布工作流。
- 不实现多节点、Kubernetes、蓝绿流量切换或真正的零停机发布。
- 不在自动回滚中恢复数据库；数据库恢复必须由运维人员明确执行。
- 不改变应用当前启动时执行 Ent Schema 迁移的行为。

## CLI 与兼容性

### 交互模式

```bash
./scripts/deploy.sh
```

无参数运行时进入向导。脚本根据 `.env.production` 和 Compose API 容器状态判断部署线路：

- 环境文件和 API 容器均不存在：首次安装；
- 环境文件存在：更新或恢复部署；
- API 容器存在但环境文件缺失：停止并报错，避免覆盖未知配置。

向导依次完成：

1. 显示检测到的部署状态；
2. 选择监听端口；
3. 选择仅本机或全部网络，默认仅本机；
4. 选择 GHCR 镜像或本地构建；
5. 镜像模式下输入镜像引用，优先使用上次部署记录；
6. 更新模式下确认备份策略和保留数量；
7. 展示不含任何密钥的部署摘要；
8. 要求明确确认后执行。

现有配置作为默认值。修改配置时原子更新环境文件，只更新向导负责的键，保留已有密钥、注释和未知配置。

### 非交互模式

继续支持：

```bash
./scripts/deploy.sh install [options]
./scripts/deploy.sh update [options]
```

保留现有参数：

- `--env-file PATH`
- `--image IMAGE`
- `--skip-backup`
- `-h, --help`

新增参数：

- `--local-build`：使用当前源码构建 API 镜像，与显式 `--image` 互斥；
- `--keep-backups N`：保留最近 N 份脚本备份，默认 7，必须为大于等于 1 的整数。

非交互模式不询问用户，不改变现有环境文件内容，适合 CI 和自动化。

## 内部结构

部署脚本按职责拆分为以下函数组：

- 输出：颜色检测、信息、成功、警告和错误；非终端输出自动禁用颜色。
- 配置：读取、原子设置、生成和校验环境变量。
- 检测：命令依赖、部署状态、当前容器和当前镜像。
- 向导：读取终端输入、选择部署模式、构建方式和确认摘要。
- 备份：创建 PostgreSQL 备份、校验、设置权限和执行保留策略。
- 发布：拉取或构建镜像、启动服务、健康检查和打印状态。
- 回滚：用部署前镜像 ID 重建 API 容器并再次健康检查。
- 记录：原子写入最后一次部署元数据。

脚本继续使用 `set -euo pipefail` 和 `flock`。所有可能失败并需要回滚的发布步骤都放在显式条件分支中，避免 `set -e` 在执行回滚前直接退出。

## 镜像与本地构建

### GHCR 镜像

1. 记录当前 API 容器所用镜像 ID；
2. 拉取指定镜像；
3. 使用 `--no-build` 重建服务；
4. 健康检查成功后记录新镜像 ID。

仍允许 `latest` 以保持兼容，但摘要中提示可变标签风险，并推荐版本标签或 digest。

### 本地构建

1. 记录当前 API 镜像 ID；
2. 执行 Compose `build --pull api`；
3. 使用本地构建结果重建服务；
4. 健康检查成功后记录新镜像 ID。

本地构建不拉取 GHCR API 镜像，但 Dockerfile 中的基础镜像仍由构建器按 `--pull` 更新。

## PostgreSQL 备份

更新默认执行备份：

1. 确认 PostgreSQL 容器存在且正在运行；
2. 将 `pg_dump -Fc` 输出写入仓库 `backups/` 下的临时文件；
3. 检查临时文件非空；
4. 通过同一 PostgreSQL 容器内的 `pg_restore --list` 校验归档可读；
5. 原子重命名为 `payment-gateway-YYYYMMDD-HHMMSS.dump`；
6. 设置权限为 `600`；
7. 按时间排序，只删除超出保留数量的脚本备份。

清理操作只匹配 `backups/payment-gateway-*.dump`，不处理其他文件。备份或校验失败时停止部署。

## 健康检查

Compose 为 API 增加容器健康检查，访问容器内 `http://127.0.0.1:8080/healthz`。

部署脚本继续从宿主机访问映射端口，并同时验证：

- HTTP 请求成功；
- 响应包含应用统一响应中的 `"status":"ok"`。

超时后打印 API 最近 100 行日志。健康检查次数保持现有的最多 90 次、每次间隔 1 秒，避免改变现有超时预期。

## 自动回滚

更新前记录当前 API 容器镜像 ID。以下任一情况触发应用回滚：

- Compose 重建失败；
- 新 API 在超时时间内未通过健康检查。

回滚过程：

1. 将 `PAYMENT_GATEWAY_IMAGE` 临时设置为旧镜像 ID；
2. 仅重建 API 服务，不重建 PostgreSQL 和 Redis；
3. 等待旧版本通过健康检查；
4. 输出回滚结果，并以非零状态结束原部署命令。

首次安装没有旧 API 镜像时不能回滚，脚本会停止失败的 API、保留 PostgreSQL/Redis 数据卷并输出排障命令。

自动回滚不恢复数据库。由于应用启动时可能执行 Schema 迁移，设计假定日常迁移保持向后兼容；若迁移不兼容，运维人员必须根据部署前备份执行人工恢复。

## 部署记录

成功部署后原子写入 `.tmp/last-deployment`，只记录：

- UTC 时间；
- 部署模式；
- 构建来源；
- 请求的镜像引用；
- 实际运行镜像 ID；
- 当前 Git 提交（可获取时）；
- 本次备份路径（如有）。

文件不记录环境变量、密码、令牌或应用密钥，权限设置为 `600`。交互向导可用其中的镜像引用作为下次默认值。

## 错误处理与日志

- 用户取消向导时返回成功状态且不修改文件或容器。
- 参数错误返回状态 2；运行时部署错误返回状态 1。
- 密钥永不打印到摘要和部署日志。
- 失败信息包含阶段名称、API 日志和可直接复制的状态/日志命令。
- 回滚成功也不会把原部署标记为成功。
- 终端使用颜色和分段提示，CI/重定向输出保持纯文本。

## 测试策略

扩展 `scripts/deploy_test.sh`，使用临时目录和 PATH 中的伪命令记录调用，不连接真实生产容器。测试按 TDD 增加：

1. 无参数时进入交互模式，首次和已有部署识别正确；
2. 向导默认仅绑定 `127.0.0.1`，并且摘要不包含密钥；
3. 原有 `install`、`update` 和参数继续工作；
4. `--local-build` 与 `--image` 冲突时拒绝执行；
5. 备份非空且通过 `pg_restore --list` 后才成为正式备份；
6. 只保留指定数量的脚本备份；
7. 新版本健康失败时按旧镜像 ID重建 API；
8. 回滚成功后原部署仍返回失败；
9. 首次安装失败时不会尝试不存在的旧镜像；
10. 成功部署记录不包含任何密钥；
11. Compose API 健康检查存在且生产配置可渲染。

最终执行：

```bash
bash scripts/deploy_test.sh
make verify
docker build -t starpay:deploy-test .
```

## 验收标准

1. 新用户可通过无参数向导完成首次部署，不需要手工编辑密钥。
2. 已有部署可复用原配置完成更新，原有密钥不改变。
3. 现有自动化调用不需要修改。
4. 更新失败时，在存在旧镜像的情况下自动恢复健康的旧 API。
5. 数据库备份经过可读性校验，并且保留策略不会删除无关文件。
6. 所有新增脚本行为都有失败先行的自动化测试。
7. 项目完整验证、容器构建和部署脚本测试全部通过。
